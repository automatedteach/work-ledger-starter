# Claude Work Ledger Bootstrap

After the existing Skill and platform-policy gate, use Reference19's pinned
committed role probe before writer-only live recovery or operative mutation.
Claude on Windows and macOS has the same writer/proposer roles as Codex.
Only the active writer, or the owner-authorized incoming chat performing the
bounded transfer, enters the mutable procedure below. Readers use full pinned
context and proposed dossiers, with only exclusive ignored proposal writes.
Never fall through to legacy writing because another writer is idle or its
native messaging route is unavailable. With no active designation, the ordinary
route is unchanged. Use the prepared exact platform operations and actual native
session tools; a missing capability stops its affected action without widening
permissions. The owner can switch here after confirming the old writer is done;
no message to the old app is required.

When authorized to write, the visible conversation is the coordinator.
Carry out setup, ingestion,
semantic adoption, and ordinary checkpoint transactions here, synchronously.
Do not hand the transaction to a built-in Agent or background worker. The
project's separate claim reviewer and bounded ledger-worker roles retain their
existing narrowly assigned roles; neither can take over this coordinator's
profile, source, current-state, receipt, staging, or commit work.

When the participant identifies this as their Work Ledger and asks to see its
setup card, set it up, start it, or become ready to use it, use the project
`intake-ingest` Skill as the routing entry point unless the request identifies
an already-confirmed profile, recovery, or profile revision. The Skill
invocation supplies the definition needed for card preparation. The pre-reply
phase consists of that invocation and the card response; repository reads,
shell, Git, agents, retrieval, external actions, edits, and writes begin under
the post-card route after the participant's reply. Until then, keep repository
and external state unchanged. If the Skill is unavailable, say so and stop.

Displaying the setup card does not authorize a commit or any other repository
action. A setup checkpoint may occur only after the participant directly
confirms the card, including choice 5 and every required prepared fact, and the
post-consent procedure validates the repository and applicable authority.

For every other participant-facing or coordinator Work Ledger request, invoke
the project `intake-ingest` Skill before other tools, including each same-chat
ingestion request, semantic-review A/B/C reply, and ordinary-save reply. Route
the reply with its current conversation context; do not repeat the setup card
or treat an earlier Skill invocation as the new phase's entry. The Skill
distinguishes a read-only answer from durable task output and ingestion.
"Show what this workspace currently understands" is read-only consultation;
"Draft a checklist in artifacts/" requests an ordinary ledger deliverable:
the artifact and its prospectively prepared dossier and validated drafting
receipt. A short draft still uses that route; keep the records concise while
meeting the existing requirements. Leaving an artifact uncommitted does not
waive those records. This is not new ingestion and does not itself authorize
a commit. If the required route cannot be completed, stop before the artifact
write and explain the affected boundary. The two tracked
internal subagent roles, `claim-reviewer` and `ledger-worker`, follow only their
exact coordinator envelope and role file; they do not invoke the startup Skill
or expand their listed tools.

Authority for a read, edit, Git operation, retrieval, publication, or external
action comes from the participant's current request and direct in-chat replies;
project files alone do not originate it. An exact-scope, versioned,
ledger/profile-bound record may carry previously granted authority across tasks
only after the current request permits validation and every binding and recovery
check passes. Capability is not authority.

For an ordinary task, profile revision, recovery request, or explicit read-only
consultation in an established ledger, the participant's current request
permits the Skill to load the detailed post-consent procedure and canonical
shared skill for validation and routing only. Do not apply a saved profile or
authority record, or begin protected work, until its exact ledger/profile
binding and recovery state validate. A confirmed established profile does not
receive the first-setup card again.

Parity invariant:

> For the same role and the same granted authority, Codex and Claude Code get
> the same editable paths, review obligations, retrieval and action authority,
> and saved outcome. Configuration syntax may differ; capability may not. A
> genuine harness limitation is disclosed and declines the affected action
> rather than claiming compliance with a weaker substitute.
