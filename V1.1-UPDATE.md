# Work Ledger v1.1: a dedicated ledger writer

Keep a regular writer conversation in Claude Code or Codex while other task
chats prepare proposed updates. Both harnesses use the same ledger roles on
Windows and Mac. One conversation at a time may change the shared ledger.

This is a fresh-install package. It adds no database, service, background agent
or required Ledger executable. Native app tools provide conversation delivery;
the ledger folder remains the common record.

## Choose your starting point

| Starting point | What to do |
| --- | --- |
| No ledger yet | Extract the named v1.1 ZIP into a new folder and follow START-HERE.md. |
| Unused v1 download | Use a separate v1.1 folder; preserve anything you already added. |
| Existing v1 or older ledger | Keep it intact. No in-place updater ships; never overlay this ZIP. |
| Customized or unknown version | Request a read-only version/customization check before any separate migration. |
| Interrupted update | Preserve the folder and complete its normal recovery first. |

A fresh start is optional. Select context deliberately through normal intake;
do not copy old profiles, current files, claim registers or recovery caches.
MIGRATE-AN-EXISTING-LEDGER.md is a reference, not a v1.1 overlay procedure.

## Finish ordinary setup

The five choices and separate ordinary-task saving opt-in are unchanged.
You may continue ordinary one-writing-conversation use without enrollment.
Use the platform's existing setup and, for Claude, its one-time prepared policy
activation. Switching writers later does not repeat setup or permission editing.

## Choose a writer

In the chat you want to use, say:

> Make this my dedicated ledger writer. Let my task chats prepare proposals
> and send the results I release here, then receive your final outcome.

The assistant checks actual identity, source/provider permissions, native tools
and your existing saving choices, then records the designation normally.
Confirm that other write-capable chats/jobs have stopped or refreshed. The
assistant handles the mechanics; designation never grants broader saving,
source access, publication or external action.

You may keep a named writer destination in each harness. Exactly one is active
for ledger changes. The other remains available for committed-context work and
pending headers, without editing the ledger. Reader chats always use the same
full saved context and prepare complete proposals; they do not change operative
ledger files or Git.

## Switch from Claude to Codex, or back

Tell the incoming writer:

> Use this chat as my ledger writer now instead of the other one. The previous
> writer has finished reconciling and saving; it and its write-capable jobs
> have stopped and will make no further changes.

Your informed confirmation is enough; no confirmation in the old app or
cross-app messaging is required. The incoming writer checks for an unfinished
update, records the transfer under your existing save permissions and continues.
A real unfinished checkpoint pauses ordinary transfer and follows normal
recovery. Merely being idle is not proof that writing has finished.

The previous chat can stay open but must read the current designation before
any later change and remain nonwriting until you switch back. Both can work
from committed context; they do not edit the shared files/index simultaneously.
An incoming writer reports a genuinely missing permission without inventing an
extra transfer ceremony. Your existing ask-before-save or owner-managed Git
choice still applies.

The app can also request permission for a particular operation. That is a
runtime permission gate; it does not add another writer-switch ceremony or
require editing the permission files.

## Review, hold and release

Ask normally in task chats. At a useful stopping point the assistant may offer
to send the result. Say "Keep this here while we revise it" to hold, or "Send
this result to the ledger writer" to release it. Completion, silence and praise
are not release. A held result stays held until you change that instruction.

A task-specific advance instruction can authorize release on completion, but
the app may still require your confirmation for the later actual send. The
tested direct-release path must not be confused with a future coordinator-cue
path that the runtime rejects. If that happens, the assistant preserves the
proposal and explains the actual send gate; it does not bypass it.

Within each harness, the assistant uses its available authorized native message
route, sends the proposal reference and returns the writer's outcome. You do
not copy or merge files. Claude-to-Codex automatic messaging is not required or
promised. If the reachable writer destination is on standby, the result stays
pending until you switch the active writer or explicitly choose another
authorized delivery route. No silent manual-forwarding baseline is used.

The active writer finishes any current checkpoint, verifies authority and exact
proposal bytes, reconciles against the latest saved context and reports every
intent: applied, already reflected, reconciled, pending or declined. Replays
do not duplicate accepted work or erase pending work; final returns do not
start acknowledgment loops.

## What a result means

| Status | Meaning |
| --- | --- |
| Answer ready | Reviewable output; no ledger save implied. |
| Proposal prepared | Proposed changes exist; ignored packets are not canonical or guaranteed backed up. |
| Submitted / received | Delivery evidence; integration may still be pending. |
| Saved with verified checkpoint | Reported changes are in local history; nothing was uploaded. |
| Pending | The named intent still needs authority, a choice or processing. |

Saving choices, source quarantine/adoption and protected review stay unchanged.
Sending a proposal does not replace any of those gates.

## Compatibility and actual evidence

The implemented roles and platform procedures target Codex and Claude Code on
Windows/macOS. Native tools, provider/account permissions and runtime behavior
can differ. The release notes distinguish implemented procedures from actual
tested app/CLI/OS combinations; a CLI test is not a Desktop test, and written
Mac commands are not an executed Mac journey. A missing concrete operation
stops that action with its reason, not all participation based on the app's name.

An implemented procedure is distinct from a standard-qualified workflow with
no routine permission dialogs. Some new operation forms have been exercised
with exact runtime confirmations. A pending request may be approved through
the app's normal permission surface when the ledger action is already
authorized. Permission approval supplies no additional ledger authority.
Denial or an unavailable approval surface stops that operation; the assistant
preserves the work without changing settings or trying another spelling.

If delivery fails, preserve the proposal and report it. An owner may explicitly
choose exact-pointer forwarding; the writer still authenticates the human task,
release and save scope. The pointer/hash alone grants nothing. No cloud account,
MCP bridge, timer or permission bypass is installed.

## Replace or disable

Explicitly request another writer or a return to serial use. Use the same
finished-checkpoint, stopped-writer and normal-save boundary. Preserve held and
pending proposals; switching never releases them. Do not reset history or paste
old rules over an enrolled ledger. Refresh stale chats before they resume.

Support details are on the release page. Include release filename, app, OS,
step and observed result, with private material removed. The complete technical
